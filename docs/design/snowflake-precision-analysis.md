# Snowflake ID 精度分析与方案对比

## 1. 当前实现

Salvo 采用经典 Twitter Snowflake 方案，64 位 ID 分配如下：

```
| 1 bit | 41 bits 时间戳(ms) | 10 bits 节点ID | 12 bits 序列号 |
```

| 部分     | 位数   | 范围         | 说明                              |
|----------|--------|--------------|-----------------------------------|
| 符号位   | 1 bit  | —            | 未使用                            |
| 时间戳   | 41 bits| ~69 年       | 毫秒精度，自 2024-01-01 起        |
| 节点 ID  | 10 bits| 0–1023       | 最多 1024 个节点                  |
| 序列号   | 12 bits| 0–4095       | 每毫秒每节点最多 4096 个 ID       |

### 单节点吞吐量

- 每毫秒 4096 个 ID = **每秒约 409.6 万个 ID**
- 对于 Salvo 压测工具，此吞吐量远超实际需求

## 2. 生产精度评估

### 2.1 毫秒精度是否够用？

**够用。** 理由：

1. **Salvo 是单进程压测工具**，不需要分布式节点协调
2. **实际 ID 生成速率远低于 409.6 万/秒**，即使 10 万并发场景也不会超过百万级
3. **Trace 时序排序依赖 `time.Time` 字段**，不依赖 ID 本身的时序精度
4. **毫秒级时间戳在 41 bits 内可覆盖约 69 年**（从 2024-01-01 起至 2093 年）

### 2.2 测试中的 ID 冲突问题

测试中出现的 ID 冲突**不是精度问题，而是使用方式问题**：

```go
// 错误：每次调用创建新 Node，同一毫秒内生成相同 ID
func newID(t *testing.T) snowflake.ID {
    n, _ := snowflake.NewNode(1)  // 每次 new，step 从 0 开始
    return n.Generate()
}

// 正确：共享单例 Node，序列号自动递增
var testNode *snowflake.Node  // 进程级单例

func newID(t *testing.T) snowflake.ID {
    return testNode.Generate()  // 同一毫秒内 step 自动 +1
}
```

**根因**：新 Node 的 `step` 从 0 开始，`lastTime` 为 0。同一毫秒内，两个独立的 `Node(1)` 会生成完全相同的 ID（时间戳相同 + 节点号相同 + 序列号都从 0 开始）。

**生产中不会出现此问题**，因为 Node 是长生命周期单例。

## 3. 更细粒度方案对比

| 方案                     | 精度    | 每节点吞吐   | 位数分配              | 适用场景               |
|--------------------------|---------|-------------|-----------------------|------------------------|
| 经典 Snowflake（当前）    | 1ms     | 409.6 万/s  | 41t + 10n + 12s       | 通用                   |
| Sonyflake                | 10ms    | 2.56 万/s   | 39t(10ms) + 8n + 16s  | 长寿命 ID、低频生成     |
| 微秒级 Snowflake         | 1μs     | 4096/s      | 51t(μs) + 4n + 8s     | 高精度时序、少量节点    |
| 百纳秒级 Snowflake       | 100ns   | 256/s       | 53t(100ns) + 4n + 6s  | 极高时序精度            |
| ULID                     | 1ms     | 1.21 万/s   | 48t(ms) + 80随机       | 无需协调、可排序        |
| UUIDv7 (RFC 9562)        | 1ms     | 随机        | 48t(ms) + 74随机       | 标准化、跨语言          |

### 3.1 微秒级 Snowflake 位分配

如果需要微秒精度，可调整 64 位分配：

```
| 1 bit | 51 bits 时间戳(μs) | 4 bits 节点 | 8 bits 序列 |
```

- 51 bits 微秒 ≈ 71 年（从 2024-01-01 起）
- 4 bits 节点 = 最多 16 个节点
- 8 bits 序列 = 每微秒 256 个 ID = **每秒 2.56 亿**

### 3.2 UUIDv7 方案

如果未来 Salvo 发展为分布式集群，可考虑 UUIDv7（RFC 9562）：

```
| 48 bits 时间戳(ms) | 4 bits 版本 | 12 bits 随机 | 2 bits 变体 | 62 bits 随机 |
```

- 无需节点协调
- 毫秒时序 + 随机尾部
- 跨语言兼容，标准化

## 4. 结论

**当前经典 Snowflake 方案对 Salvo 完全够用，无需调整。**

| 评估维度   | 结论                                         |
|------------|----------------------------------------------|
| 吞吐量     | 409.6 万/s，远超压测工具需求                  |
| 时序精度   | 毫秒级足够，Trace 排序依赖 time.Time 字段     |
| 节点容量   | 1024 节点，单进程工具绰绰有余                 |
| 使用注意   | 确保 Node 为进程级单例，避免重复创建           |
| 扩展方向   | 如需分布式，可迁移至 UUIDv7                   |
